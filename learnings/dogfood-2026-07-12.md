## 实验 1 — 正门与工具分发(D42 REPL UX)

**题目**:裸敲 `oh`;敲 `/` 看补全菜单;看底部状态行。然后问:
`引擎主循环在哪个文件?`
**预期**:一个词进会话;工具调用实时可见;答案应指向 `engine/query.py`。

**结果**:
- 进入 REPL,banner `oh chat — multi-turn REPL. Type / for the command menu`
- 模型调 Grep(命中噪声不小:cli.py、spike 脚本、gate.py 都进了结果),
  但综合后答案正确:`src/openharness/engine/query.py` 第 177 行 `run_query`,
  并引用了模块 docstring 佐证

**分析**:正门 ✓、工具实时显示 ✓、检索噪声大但合成正确——模型的价值恰恰
在噪声里挑对信号。D42 的"回忆税"修复在作者本人身上首次生效。

## 实验 2 — 多轮续接 + /compact

**题目**:不退出,追问六个字:`那压缩在哪介入?`(不重复任何上下文)。
然后敲 `/compact`。
**预期**:能对上"压缩在**引擎循环**里的介入点"这个指代 = carry-forward
成立;/compact 应压缩两轮重对话。

**结果**:
- 指代消解成功,答案给出两个介入点(主动 `query.py:224-241` 在 PreApiCall
  hooks 之前;被动 `272-325` 捕获 PromptTooLongFailure 后)+ 五文件分工表
  + L1 microcompact 独立路径说明——结构完整、大体准确
- **但含一处细节错误**:称被动截断"对 messages 做 head-tail truncate"。
  实际代码是 `drop_oldest_tool_pair`(丢最老的一对 tool_use/tool_result,
  上限 3 次);head-tail truncate 真实存在但属于 Layer 1(单条工具结果的
  掐中段),模型把第一层的策略安到了第三层头上
- `/compact` 返回 `(/compact: nothing to summarize)`——两轮上万字符的
  对话,拒绝压缩

**分析**:
1. carry-forward ✓(benchmark 零覆盖区拿到目击证据)
2. **"原料全真、装配全错"标本**:错误里没有一个词是编的,两个机制都真实
   存在,只是绑错了——自信、流畅、细节错,与分类学发现三(模型对自身
   正确性零校准)同族。这类错误人不读代码根本听不出来
3. **F1(飞轮进料)**:`full_compact` 的 `len(messages) <= _PRESERVE_RECENT(=12)`
   守卫把用户显式命令也拦了,且"nothing to summarize"不真实(有东西,
   只是不到 12 条)。显式命令应尊重用户意图或如实报告拒绝理由

## 实验 4 — 机器门契约(headless fail-closed)

**题目**:
```
oh ask -p "创建 /tmp/dogfood-test.txt 写入 hello" --output-format json
OPENHARNESS_PERMISSIONS__ALLOW="Write(**)" oh ask -p "同上" --output-format json
```
**预期**:第一条被拒(无人可问,fail-closed);第二条放行。

**结果**:
- 第一条:`permission_denied tool=Bash tier=headless_failclosed`,模型
  转向解释并提出替代方案,JSON envelope 干净退出 ✓
- 第二条:**Bash 拒(turn 1)之后 Write 也被拒(turn 2)**——与预期不符!
  模型的诊断正确:"`/tmp/...` 在项目根目录之外,被安全策略拒绝"

**分析**:
1. fail-closed 姿态 ✓
2. **F2(飞轮进料,预期外发现)**:文件工具 allow 规则是 **cwd 相对 glob**
   (rules.py 设计),`Write(**)` = "cwd 里随便写",够不到 /tmp。benchmark
   里 workspace=cwd 所以从未暴露。headless 授权 cwd 外路径目前**表达不出来**
   ——出题人(Claude)按 Claude Code 绝对路径语义想当然,题目本身撞出了
   语义边界。待拍板:支持绝对路径 specifier(甲)vs 只修拒绝信息(乙)
3. 有趣对照:本实验模型诊断**正确**,实验 5 同主题下它却编造了配置格式
   ——同一模型对同一系统的自述,正确性不稳定

## 实验 5 — verify gate + 修复循环(loop-runtime 皇冠)

**题目**:
```
OPENHARNESS_PERMISSIONS__ALLOW="Write(**),Edit(**)" oh ask -p \
  "在 /tmp/dogfood 目录创建 fizzbuzz.py,实现标准 fizzbuzz(1到15)打印" \
  --verify "python3 /tmp/dogfood/fizzbuzz.py" --max-iter 3 --output-format json
oh run show <run_id>
```
**预期**:门以 exit code 判定完成;修复循环把 gate 反馈喂回下轮。
(出题时未预见 F2 会让它必败。)

**结果**:
- 3 轮尝试全败:10 条 `permission_denied`(Bash × 8、Write × 2)跨 3 个
  run_id;`verification.passed: false`,returncode 2(文件不存在),
  `attempts: 3`,exit 信息如实:"repair loop did not pass verification"
- journal 8 事件完整(run_started → 3×attempt → run_finished),
  `oh run show` 单命令重建全案 ✓
- 模型最终答复:诊断正确(headless 需显式 allow;/tmp 在 cwd 外),但
  给出的修复建议是往"harness 配置"里加 **YAML `permissions: allow:` 块**
  ——OH 没有 YAML 配置,全部走 env/settings
- **副产品**(实验 6 的 git status 才暴露):repo 根目录出现 `?? fizzbuzz.py`
  ——模型被 /tmp 拒后**自适应改道**写进了 cwd(那里 `Write(**)` 放行),
  但 gate 检查 /tmp 路径,照样判败

**分析**:
1. 因 F2 实验必败,但**失败本身是满分演示**:①权限墙在 16 turn 修复压力
   下没弯;②门只认 exit code,模型再流畅的解释也过不了(发现三的现场版);
   ③journal/inspection 链路 = benchmark 归因用的同一套机制
2. **F3(飞轮进料)**:改道写 cwd 是 **A5"被拒后行为"的活样本**——没有
   原样重试,换了路(这正是 P1 eval 要测的轨迹不变量);同时实证了
   `--isolate` 的存在意义:无隔离修复循环会把副产品拉进活仓库
3. **F4(飞轮进料)**:编造 OH 配置格式——原料半真(别的系统确实这么配),
   对宿主系统的自述全错。改进方向在错误消息侧:内嵌正确的 env 示例,
   让模型转述时有真话可抄;A6 错误恢复 eval 的 case 源

eval 不是纸面数字,它预测了真实使用里哪会好、哪会坏。

## 教学沉淀(补课两则,考核已过)

1. **三层"变小"机制**:Layer 1 = head-tail truncate(**单条**工具结果,
   返回瞬间掐中段)/ 主动压缩 L2-L4(每次请求**前**,token 占比 >0.83
   分级升级)/ 被动 reactive(PTL 异常**后**,`drop_oldest_tool_pair`
   ≤3 次;丢"最老"因近因性,丢"一对"因孤儿 tool_result 会被 API 拒收)。
2. **headless 四栏合同**:目标(prompt)/ 权限(ALLOW env,headless 唯一
   授权通道)/ 完成判据(`--verify` exit code | `--goal-condition` judge)/
   预算(`--max-iter` / `--max-turns` / `--timeout`);回执 = JSON envelope
   + exit code + run journal。headless 全部表面即此四栏,其余是管道。
